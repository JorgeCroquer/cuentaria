## Problem Statement

Como desarrollador (y único usuario) de Cuentaria, hoy tengo el diseño completamente documentado pero **no existe ningún proyecto que compile ni que abra en mi teléfono**. No puedo construir ninguna capacidad de finanzas (registrar cuentas, sobres, movimientos) hasta que exista una base que: compile, corra en Android, imponga las fronteras entre contextos que el diseño exige, y tenga una red de seguridad (CI) para no romper nada al crecer.

Sin un esqueleto consistente desde el inicio, cada feature posterior tendría que volver a litigar la configuración del proyecto (estructura de paquetes, manejo de estado, fronteras de módulos, despliegue), con riesgo de una base incoherente y difícil de extender. El objetivo del proyecto es justamente que sea **barato de modificar y fácil de agregar features**; eso empieza por un scaffold disciplinado.

## Solution

Un **monorepo Melos** con el esqueleto hexagonal del único contexto del MVP (Contabilidad/Cash) más los paquetes de soporte, y una **app Flutter que arranca a una pantalla placeholder en Android y Web**, con **CI en verde** y **deploy automático de la Web a GitHub Pages** en cada merge a `main`. iOS queda cableado en el proyecto pero no se compila en CI (requiere Mac). No hay lógica de dominio todavía — eso lo trae C1; F1 entrega exclusivamente la **fundación navegable y extensible**.

Concretamente, al terminar F1 puedo: clonar el repo, correr `melos bootstrap`, abrir la app en mi Android y en una URL pública, y tener confianza de que las fronteras entre paquetes, el bus de eventos y las convenciones de estado/DI ya están fijadas para que cada feature siguiente solo "se enchufe".

## User Stories

1. Como desarrollador, quiero un monorepo Melos con paquetes Dart por contexto, para que las fronteras entre bounded contexts sean explícitas y obligatorias desde el día uno.
2. Como desarrollador, quiero que el workspace completo compile con un solo `melos bootstrap` + build, para no perder tiempo en setup manual por paquete.
3. Como desarrollador, quiero un paquete `shared_kernel` con value objects puros (`Money`, `CurrencyCode`, `AccountId`, `EnvelopeId`, `EventId`, timestamp), para reutilizar tipos base sin acoplar contextos entre sí.
4. Como desarrollador, quiero que `shared_kernel` contenga **solo** value objects sin comportamiento de ningún contexto, para que se mantenga como núcleo puro y estable (ADR-0005).
5. Como desarrollador, quiero un paquete `messaging` con el puerto `EventBus` y el tipo base `DomainEvent`, para que los contextos publiquen y reciban eventos de dominio sin importar el `domain/` ajeno.
6. Como desarrollador, quiero una implementación síncrona en proceso del `EventBus` en F1, para que el composition root sea real y C1 pueda emitir eventos enchufándose directamente.
7. Como desarrollador, quiero que el `EventBus` tenga una interfaz simple, estable y testeable (publish/subscribe), para que se sustituya por un bus de red al partir a microservicios sin tocar contratos (ADR-0005).
8. Como desarrollador, quiero el paquete `contabilidad` con el esqueleto hexagonal vacío (`domain/`, `application/`, `infrastructure/`), para que C1 tenga dónde aterrizar el dominio sin reorganizar la estructura.
9. Como desarrollador, quiero reglas de lint/imports que prohíban importar el `domain/` de otro contexto, para que las fronteras se cumplan automáticamente y no por disciplina manual.
10. Como desarrollador, quiero que las referencias entre contextos sean por ID (no por import de dominio), para preservar la separación de bounded contexts (ADR-0005).
11. Como usuario, quiero que la app abra en mi teléfono Android mostrando una pantalla placeholder, para confirmar que la fundación corre en mi dispositivo primario.
12. Como usuario, quiero poder abrir la app en una URL web (vista de conveniencia), para acceder sin instalar desde un PC.
13. Como desarrollador, quiero el runner de iOS configurado en el proyecto aunque no se compile en CI, para poder construirlo más adelante en una Mac sin retrabajo.
14. Como desarrollador, quiero navegación declarativa con go_router, para que añadir pantallas de features futuras siga un patrón consistente.
15. Como desarrollador, quiero Riverpod cableado en el composition root, para inyectar puertos→adaptadores con seguridad en compilación y exponer estado a la UI.
16. Como desarrollador, quiero un tema simple aplicado, para que la app tenga una apariencia coherente base (sin design system completo todavía).
17. Como desarrollador, quiero una pipeline de CI en GitHub Actions que corra `flutter analyze`, `dart format` (fallando si hay diff), `flutter test` y un build de Web, para detectar regresiones en cada cambio.
18. Como desarrollador, quiero que cada merge a `main` publique la Web a GitHub Pages, para que "abrir en PC" signifique abrir una URL real sin pasos manuales.
19. Como desarrollador, quiero un README mínimo con cómo levantar el proyecto (`melos bootstrap`, correr Android/Web), para retomar o transferir el proyecto sin fricción.
20. Como desarrollador, quiero tests unitarios de los value objects de `shared_kernel`, para garantizar igualdad, validación y aritmética (p. ej. de `Money`) correctas.
21. Como desarrollador, quiero un test del `EventBus` que verifique publica→recibe entre suscriptores, para asegurar el comportamiento del módulo profundo de F1.
22. Como desarrollador, quiero un widget smoke test que verifique que la app arranca y muestra el placeholder sin crash, para proteger el wiring de Riverpod/go_router en CI.
23. Como desarrollador, quiero tests de integración en los *seams* entre módulos (p. ej. un contexto de prueba publicando un evento que otro suscriptor recibe a través del `EventBus`), para validar que la composición funciona, no solo las piezas aisladas.
24. Como desarrollador, quiero que la suite de tests corra en CI y bloquee el merge si falla, para mantener la base siempre en verde.

## Implementation Decisions

**F1-1 — Alcance del scaffold: mínimo navegable, solo ruta MVP.** F1 entrega un esqueleto que compila y abre, sin lógica de dominio. **No** se crean paquetes vacíos para los contextos no-MVP (Patrimonio, Portafolio, Deudas, Tasas) ni un design system completo — emergen con su propio PRD. Evita estructura especulativa (coherente con el principio de no abstraer antes de tiempo).

**F1-2 — Plataformas.** **Android es el primario.** **Web** es objetivo secundario de conveniencia (vista ligera, sin instalar) que se mantiene porque cablearla es casi gratis; ambas compilan-y-abren en F1. **iOS** queda con el runner configurado pero **no** se compila en CI hasta tener una Mac. **Desktop nativo (Windows/macOS/Linux) fuera del MVP**, añadible después sin reescritura. La decisión de seguridad/persistencia de la Web (persistencia degradada, vista de solo-lectura, o eliminarla) se **difiere a F2**; el teléfono conserva cifrado fuerte (SQLCipher nativo) en cualquier caso.

**F1-3 — CI/CD + deploy.** F1 incluye CI (build + análisis estático para Android y Web) **y** deploy automático de la Web en cada merge a `main`. **Host = GitHub Pages** (mínima fricción: cero cuentas nuevas, publica desde el mismo GitHub Actions). Esto **modifica ADR-0004**, que había elegido Cloudflare Pages; Cloudflare queda como ascenso opcional (CDN/dominio) — mover hosting estático es solo republicar archivos.

**F1-4 — Planta de paquetes (Melos):**
- `app/` — app Flutter: UI, navegación, tema y composition root (wiring de dependencias).
- `shared_kernel/` — value objects puros compartidos.
- `messaging/` — puerto `EventBus` + tipo base `DomainEvent` (paquete propio, **no** dentro de `shared_kernel`, que se mantiene como solo value objects — refina ADR-0005).
- `contabilidad/` — contexto del MVP, esqueleto hexagonal vacío (`domain/`, `application/`, `infrastructure/`); C1 lo llena.

**F1-5 — Estado + DI del `app`: Riverpod + go_router.** Riverpod unifica manejo de estado e inyección de dependencias con seguridad en compilación: los providers cablean puertos→adaptadores y permiten *overrides* con adaptadores falsos en tests; go_router para navegación declarativa. Es la **convención para toda feature futura**. Vive solo en `app`; el dominio Dart puro no depende de él → reversible con costo medio. **Candidata a ADR-0012** (decisión pegajosa, con trade-off real frente a Bloc y get_it+provider).

**F1-6 — Profundidad del `messaging` en F1.** Puerto `EventBus` + tipo `DomainEvent` + **implementación síncrona en proceso** + smoke test (publica→recibe). No es abstracción prematura: es el contrato mínimo que C1 necesita para emitir eventos.

**Módulos a construir (sketch).** El **módulo profundo** de F1 es `messaging` (mucho comportamiento futuro tras una interfaz publish/subscribe simple y estable). `shared_kernel` es un conjunto de value objects puros y testeables. `contabilidad` es estructura vacía. `app` es composición/orquestación.

**Enforcement de fronteras.** Límites de paquete Melos + reglas de lint de imports que prohíben importar el `domain/` de otro contexto; comunicación entre módulos solo por eventos de dominio (vía `messaging`) y API de aplicación delgada; referencias por ID.

## Testing Decisions

**Qué hace un buen test:** verifica **comportamiento externo** observable (la interfaz pública de un módulo), no detalles de implementación; un refactor interno que preserva el contrato no debe romper el test. Cobertura amplia: **todo lo testeable de F1 se testea**, incluyendo **tests de integración donde haya *seams*** entre módulos o dentro de un módulo.

- **`shared_kernel` (unit):** igualdad/valor, validación e invariantes de los value objects; aritmética y reglas de `Money`/`CurrencyCode`.
- **`messaging` (unit + integración):** publica→recibe con uno y varios suscriptores; orden de despacho síncrono; que un publicador y un suscriptor desacoplados se comuniquen solo a través del puerto (seam entre módulos).
- **`app` (widget smoke test):** la app arranca, resuelve sus providers de Riverpod y muestra la pantalla placeholder sin crash; navegación go_router a la ruta inicial.
- **Integración en seams:** un contexto de prueba que publica un `DomainEvent` y otro suscriptor que lo recibe a través del `EventBus`, validando la composición real (no solo unidades aisladas).
- **CI:** la suite corre en GitHub Actions y bloquea el merge si algo falla.

**Prior art:** ninguno — F1 es greenfield. Estos tests **establecen los patrones de referencia** (unit de value objects, test de puerto/bus, widget smoke, integración por el bus) que los PRDs siguientes reutilizarán.

## Out of Scope

- Lógica de dominio del ledger (agregados Cuenta/Sobre, postings, invariante auto-balanceado, `registrar(...)`) → **C1**.
- Persistencia local cifrada (Drift + SQLCipher, event store) y la decisión de seguridad de la Web → **F2**.
- Paquetes de los contextos no-MVP: Patrimonio, Portafolio, Deudas, Tasas.
- Design system completo (F1 solo trae un tema simple).
- Sync, Auth y E2EE → **F3**. Export → **F4**.
- iOS en CI (requiere Mac) y desktop nativo (Win/macOS/Linux).
- Cualquier integración externa, servicio de tasas o UX de captura rápida.

## Further Notes

- **Refinamientos de diseño propagados en esta sesión:** ADR-0004 (GitHub Pages en vez de Cloudflare), ADR-0005 (EventBus vive en `messaging`, no en `shared_kernel`), Overview §6 (plataformas: Android primario + Web conveniencia; desktop fuera del MVP). Ver notas Obsidian `04`, `06` y `08`.
- **ADR-0012 pendiente:** formalizar la elección Riverpod + go_router (F1-5).
- **Riesgo conocido diferido:** el modelo de amenaza de la Web (cifrado en reposo del navegador) se resuelve en F2, no en F1.
- **Orden de construcción del MVP:** F1 → F2 → C1 → C2 → S2 → U1. **Orden de definición** de PRDs: F1 → **C1** (siguiente) → F2 → C2/S2 → U1.
